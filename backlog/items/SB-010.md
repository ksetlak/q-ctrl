## Description

Operators currently cannot edit a ticket's fields after creation without opening the `.md` file in a text editor. This ticket adds an edit dialog that opens when the operator clicks a card, allowing them to update `title`, `priority`, `type`, `milestone`, and the Markdown body directly from the app. The dialog reads the current values from the file on open and writes them back on confirm. `id` and `status` are display-only — status is changed via drag-and-drop (SB-007), not here.

## Acceptance Criteria

- [x] Clicking a card (without initiating a drag) opens an edit dialog pre-populated with the ticket's current `title`, `priority`, `type`, `milestone`, and body text.
- [x] `id` and `status` are shown as read-only labels in the dialog — they are not editable fields.
- [x] The dialog exposes the following editable fields: `title` (text input), `priority` (dropdown: must / should / could), `type` (dropdown: feature / bug / chore / docs / test / setup / infra), `milestone` (text input), and body (multi-line text area).
- [x] Confirming the dialog writes only the changed fields back to the ticket's `.md` file on disk, preserving all other frontmatter fields (including `order`, `dependencies`, `references`) verbatim.
- [x] The board card updates immediately after save without a full reload.
- [x] Cancelling the dialog discards all changes and leaves the file untouched.
- [x] If the file write fails, the dialog shows an inline error and remains open so the operator can retry or cancel.
- [x] A click that travels more than ~4px from its start point is treated as a drag (SB-006/SB-007) and does not open the edit dialog.

## Notes

**Click vs drag disambiguation:** `TicketCard` already handles `card-pressed`, `card-moved`, and `card-released`. Add a `drag-distance` accumulator in the window: on `card-released`, if total pointer travel is ≤ 4px and no column change occurred, treat it as a click and fire `card-clicked(id)` instead of `reorder-ticket`. The 4px threshold prevents accidental edits from imprecise clicks.

**Dialog reuse:** The existing `NewItemDialog` component covers title + priority only. Rather than extending it (which would complicate the create flow), add a separate `EditItemDialog` component that takes a full `TicketData` plus body string. Rust populates it via `set_edit_*` properties when `card-clicked` fires, and reads back via `on_edit_confirmed`.

**Body editing:** Slint's `TextEdit` widget (from `std-widgets.slint`) provides multi-line input. The body is the raw Markdown string below the `---` delimiter — pass it as-is, write it back as-is. No Markdown rendering needed in M2.

**Field write strategy:** Parse the frontmatter as a line-by-line string replacement (same pattern as `write_order` and `write_status` in `ticket.rs`) rather than a full serde_yaml round-trip, to avoid reformatting unrelated fields. Replace each edited field's line individually; replace the body section wholesale.

**`TicketData` extension:** Add `body: string` and `ticket-type: string` and `milestone: string` fields to the Slint struct so the edit dialog can be pre-populated without a separate Rust callback. Update `to_ticket_data()` and the `TicketFrontmatter` deserializer accordingly. Also add `ticket_type` and `milestone` to `TicketFrontmatter` in `ticket.rs`.
