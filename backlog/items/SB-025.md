## Description

Today `order: 0.0` doubles as the "unordered" marker, but a drop on the board can compute exactly 0.0. Dropping SB-024 at the top of READY, above a card with order 1.0, wrote `1.0 - 1.0 = 0.0`, so pickup treated a deliberately placed ticket as unordered. The fix is to make "unordered" mean one thing only: the ticket has no `order` value. `0.0` becomes an ordinary number.

Two rules follow:

- **Created programmatically** (by an agent, a script, or by hand from the template): the ticket has no `order`. This is legitimate.
- **Placed in the GUI** (dropped on a column, or created with the new-item button): the ticket always ends up with an order that matches where it appears on the board. A graphical placement can never leave a ticket unordered.

## Acceptance Criteria

- [ ] A ticket with no `order` key, or with an empty or `null` value, loads as unordered. The app no longer turns a missing value into 0.0.
- [ ] Within a column, unordered tickets are shown after every ordered ticket, then by ID. This matches the pickup rule.
- [ ] `0.0` is treated as a normal order value, in the app's sorting and in its drop calculations.
- [ ] Every drop (top, bottom, between cards, empty column, cross-column) writes a real order, and the ticket appears exactly where it was dropped.
- [ ] Dropping into a column that contains unordered tickets still works. Dropping above or between ordered tickets uses their values. Dropping below the last ordered ticket, or onto the unordered ones, gives the unordered tickets orders too, or places the dropped ticket so the visible order matches what gets written. After the drop, saved orders and the visible order agree.
- [ ] Creating a ticket with the new-item button writes an order that places it at the bottom of the OPEN column, where it appears.
- [ ] The fallback in `main.rs` that writes `0.0` when a drop has no position is replaced with a real computed order.
- [ ] Unit tests cover: a missing or null order, unordered tickets sorting last, a drop that computes 0.0 and keeps it, each drop position above, and creation through the GUI path. All current tests pass.
- [ ] Existing tickets in this repository that carry `order: 0.0` as the old marker are migrated to no `order`, so they stay unordered.

## Notes

Needs a matching change in Scaffold, shipped before or together with this one:

- Ticket template: leave out `order` instead of `order: 0.0`. Recommended over `order: null`: the app and pickup must already handle a missing key, so one representation of "unordered" keeps things simple, and agents following "leave `order` as in the template" then write nothing. The app should still accept an empty or `null` value without error.
- `backlog/README.md`: the `order` row says a missing value or `0.0` means unordered. It should say only a missing value does, and that `0.0` is a real position.
- `pickup` skill, selection step 5: unordered means no `order` value, not `0.0`.

Migration matters: once `0.0` counts as an ordered value, any ticket still carrying the old template default jumps to the top of the pickup order. Projects updated through Copier will have such tickets, so the Scaffold release that makes this change needs a clear migration note.

Likely places in the code: `compute_order` and `order_for_drop` in `ticket.rs`, the `order: f64` field, the sort in `load_tickets`, `create_ticket`, and the drop handler in `main.rs`.
